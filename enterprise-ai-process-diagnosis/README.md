# 企业 AI 应用诊断（改造方）

这是康嘉鑫的个人实验版 Skill，用于把一个具体企业流程的证据转成业务诊断、技术可行性判断和3至7天影子试点。

它不再只回答“应该用工作流还是 Agent”，还会明确：

- 当前真实证据支持什么，哪些结论被禁止；
- 业务需求是否成立，流程是否应先改造；
- 每个技术组件是`可开发`、`有条件`还是`阻塞`；
- API、文件导入、RPA或人工观察分别在什么条件下成立；
- 第一轮实际构建哪些组件、字段、状态、异常和验收记录。

## 推荐输入

优先使用 `$enterprise-material-analysis` 形成的证据包，或 `$enterprise-workflow-mapping` 形成的员工确认流程卡。复杂原始材料不要直接跳过证据整理。

## 你可以直接这样说

- “用这份企业材料证据包诊断流程，并判断当前能开发到什么程度。”
- “先核对 OA 和 ERP 系统接口条件，再给出条件式技术方案。”
- “为这个流程设计一个3至7天离线影子试点，写清组件、字段和验收。”

## 输出

内部版包含证据冲突、禁止结论、业务判断、系统接口发现卡、条件式技术方案、组件可行性和试点。客户版使用相同事实与风险，但改成业务语言。

模拟案例见 `evals/fixtures/urgent-procurement/actual-diagnosis.md`。

## 当前边界

- 一次只诊断一个具体流程，不做整家企业成熟度审计。
- 不替代员工访谈和复杂材料证据整理。
- 不直接开发或修改生产系统。
- 接口、权限、部署或安全未知时，不承诺生产集成。
- 首个验证平台是 Codex；尚未公开发布。

## 本地安装与验证

当前由本地安装过程复制到个人 Skill 目录，没有真实可用的公共 `npx skills add` 安装命令。包结构、触发边界、输出契约和模拟证据包案例均使用本地自动检查；这不等同于真实企业试点或独立模型运行验证。

本地验证命令：

```bash
python3 -m unittest discover -s enterprise-ai-process-diagnosis/tests -v
```

## Troubleshooting

- 如果它把材料口述当运行事实，检查证据包的 claim IDs、冲突和禁止结论是否被继承。
- 如果它直接推荐 Agent 或某个产品，检查最小充分路线和系统接口发现卡。
- 如果技术方案看似具体但没有事实条件，要求给每个组件标记`可开发/有条件/阻塞`。
- 如果接口未知，第一轮应退回离线文件或人工观察，不得虚构 API。
