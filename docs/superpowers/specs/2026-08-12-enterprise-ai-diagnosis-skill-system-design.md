# 企业 AI 应用诊断 Skill 系统设计

## 1. 目标

构建一组可组合的个人 Skill，为企业 AI 应用数字化改造提供从员工工作摸排、改造方访谈准备、材料分析，到机会识别、技术路线判断和可视化改造档案的连续方法。

第一版不开发统一员工入口，也不做生产系统接入。先在 Codex 中验证 Skill 之间的输入输出和多类模拟案例。

## 2. 产品边界

### 客户侧

客户侧只暴露 `enterprise-workflow-mapping`：

- 使用者是普通企业员工；
- 每次只梳理一项具体、高频工作；
- 通过 10-15 个主问题和动态追问还原实际流程；
- 接受可选的录音转写、纪要、SOP、Excel、CSV、PDF、Word、截图和 Markdown；
- 输出员工确认的“岗位工作流程卡”；
- 不展示 Agent、RPA、RAG、技术路线、降本预测或最终改造结论。

客户侧不暴露改造方访谈问题库、机会排序规则和内部诊断过程。

### 改造方侧

改造方使用私有的 `enterprise-ai-application-diagnosis` 总控 Skill：

- 生成按行业、部门、岗位定制的访问名单、问题清单和追问路线；
- 汇总多个员工流程卡、访谈纪要和业务材料；
- 区分口述、制度、样本、系统记录和推测证据；
- 将工作拆成流程节点，识别规则、工作流、API、RPA、AI 工作流、RAG、边界 Agent 和人工的责任；
- 形成改造优先级、试点方案和客户沟通材料；
- 输出可视化企业 AI 应用改造档案。

### 明确不做

- 不让客户员工直接看到改造方模式；
- 不让 AI 直接替企业确认业务事实或自动执行高风险动作；
- 不承诺未经测量的降本增效；
- 不因客户提出“Agent”就默认推荐 Agent；
- 不在第一版开发统一 SaaS、账号体系、跨员工实时通信或生产系统写回。

## 3. Skill 组成

```text
enterprise-ai-application-diagnosis（改造方总控，私有）
├── enterprise-workflow-mapping（员工侧摸排）
├── enterprise-interview-preparation（改造方访谈准备）
├── enterprise-material-analysis（材料提取与证据整理）
└── enterprise-transformation-visualization（方案图表与档案输出）
```

当前已存在的 `enterprise-ai-process-diagnosis` 作为改造方诊断核心，后续由总控 Skill 调用或迁移；不在本规格中直接删除旧目录。它不承担员工访谈、复杂材料证据整理或最终可视化渲染。

截至 2026-08-12 的本地实现状态：

- `enterprise-workflow-mapping`：已完成个人实验版；
- `enterprise-material-analysis`：已完成个人实验版，可输出材料清单、证据账本、冲突、覆盖缺口和最小补证请求；
- `enterprise-interview-preparation`：尚未独立封装；
- `enterprise-transformation-visualization`：已有单个可视化原型，尚未封装；
- `enterprise-ai-process-diagnosis`：诊断核心已升级到 0.2.0，可消费材料证据包、继承禁止结论、判断组件级可开发性并输出条件式技术方案；
- `enterprise-ai-application-diagnosis`：多 Skill 总控尚未完成。

子 Skill 不互相循环调用。总控根据任务阶段调用子 Skill，所有交接通过标准 Markdown/JSON 档案完成。

## 4. 启动协议

### 员工侧

Skill 描述必须覆盖以下自然语言意图：

- “帮我摸排一项日常工作”；
- “梳理我的工作流程，看看哪里可以优化”；
- “我是销售/财务/客服，想记录一项重复工作”；
- “请通过提问了解我的工作，并生成流程卡”。

员工只需说：

```text
使用企业工作摸排 Skill，帮我梳理一项日常工作。
```

Agent 首次响应只显示简洁说明和三项必要信息：部门、岗位、具体工作。若员工未指定任务，Agent通过“每天/每周最耗时或最易出错的工作”帮助其选择，不展示内部模式菜单。

### 改造方侧

总控 Skill 由以下意图触发：

- “为这个行业/部门/岗位生成访谈提纲”；
- “分析这些会议纪要、录音转写和业务材料”；
- “把多份流程卡汇总成 AI 改造方案”；
- “判断这个节点应该用规则、工作流、RPA、AI 还是 Agent”。

## 5. 员工摸排流程

员工侧每次只问一个问题，主问题控制在 10-15 个，动态追问控制总时长约 15-25 分钟。六段逻辑对员工隐藏：

1. 确定任务：名称、频率、触发事件、交付对象；
2. 还原步骤：从输入到输出的实际操作顺序；
3. 信息与工具：系统、表格、聊天、文件和重复录入；
4. 判断与异常：判断依据、例外、审批和人工接管；
5. 影响与负担：耗时、数据量、等待、返工、错误后果；
6. 证据与确认：上传材料、标记证据等级、让员工修改并确认流程卡。

员工侧可以暂停和继续；材料上传是可选项。没有材料支持的内容必须标记为“员工口述，待核实”。

## 6. 共享档案契约

### 岗位工作流程卡

每次员工摸排生成一个 Markdown 文件，并可附带 JSON：

```yaml
record_type: workflow_card
schema_version: "0.1"
project_id: "企业项目代号"
department: "部门"
role: "岗位"
work_name: "具体工作"
trigger: "触发条件"
frequency: "频率"
consumer: "结果使用者"
steps: []
systems: []
inputs: []
outputs: []
decision_points: []
exceptions: []
burden: {}
evidence: []
open_questions: []
employee_confirmed: false
```

每个步骤至少包含：由谁做、输入是什么、使用什么、做什么、输出什么、判断依据、异常怎么办、证据等级。

### 原始材料与完整性记录

员工生成的流程卡是“员工确认后的陈述”，不是不可质疑的企业事实。第一版和未来统一入口都保留三层记录：

1. `raw_submission`：员工原始回答、原始上传文件及提交时间；
2. `employee_confirmed_card`：Agent整理后由员工确认的流程卡；
3. `diagnostic_derivation`：改造方对流程卡的合并、质疑、补证和诊断结论。

每份记录包含唯一编号、创建时间、来源角色、文件清单、文件哈希、版本号和上游记录编号。修改流程卡时创建新版本，不覆盖已确认版本，并记录修改人、时间和说明。

这套记录只能发现提交后的删改，不能证明员工在提交前披露了全部事实。降低故意遗漏风险需要多岗位交叉访谈、系统或脱敏样本核对、主管确认、冲突提示和调研覆盖率检查。没有提交材料不能被解释为该流程或问题不存在。

### 证据等级

- `E1`：脱敏样本、截图、系统记录或实际操作观察；
- `E2`：多角色访谈或带具体例子的会议/录音转写；
- `E3`：单个员工口述；
- `E4`：SOP、制度或流程图；
- `E5`：模型推测，只能作为待验证线索。

## 7. 改造方输出

总控完成材料分析后生成两层结果：

### 内部诊断档案

- 调研覆盖范围和未覆盖岗位；
- 当前流程图；
- 节点级问题与证据；
- 不同岗位描述的冲突；
- AI 应用机会矩阵；
- 节点责任分配和被排除路线；
- 数据、权限、系统接口和维护责任；
- 试点范围、指标、停止条件和人工接管；
- 待确认事项。

### 客户沟通版

- 已确认的业务问题；
- 推荐的改造方向；
- 需要客户提供的材料和参与人员；
- 试点计划和验收方式；
- 责任边界、风险和不在范围内的事项。

## 8. 可视化要求

图表优先，文字结论作为图表旁的摘要，证据可展开查看。第一版输出至少包含：

1. 调研覆盖图；
2. 当前流程图；
3. 问题节点分布图；
4. AI 应用机会矩阵；
5. 改造后流程图；
6. 试点路线图。

图表使用自然语言节点和角色标签，避免大段箭头、装饰性符号和“AI味”流程文案。每个节点必须可追溯到证据记录或明确标记为推测。

## 9. 路线判断

按节点而不是按项目整体选型：

- 固定条件、阈值、校验：确定性规则；
- 固定顺序、状态、重试：工作流；
- 有正式接口：官方 API；
- 无 API 且只能操作浏览器/桌面：授权 RPA；
- 文本理解、分类、摘要、草稿：AI 工作流；
- 需要查权威资料：RAG；
- 需要有限动态判断和工具选择：有边界 Agent；
- 高风险、审批、付款、客户承诺：人工。

CRM 场景允许规则、AI 分析和边界 Agent 并存，但必须分别验证新增发现的价值、误报和人工复核成本。

## 10. 第一版验收

先用模拟企业案例，不开发统一入口。至少准备三个互不相同的案例：

- CRM 销售运营复盘；
- 影刀 AI 新闻日报；
- 一个最终应采用普通规则/工作流、不应上 Agent 的反例。

每个案例至少包含两种角色的材料、一个异常分支、一个真实或脱敏样本和一项可测量的试点指标。验收重点是：能否从原始材料生成流程卡、识别证据冲突、给出节点级路线、生成可视化改造档案，并在反例中明确排除 AI/Agent。

## 11. 未来统一入口

验证通过后再开发客户侧网页或企业内部入口。入口调用的是客户摸排 Agent；改造方总控 Agent 通过受控后台处理原始提交、已确认流程卡和材料。两者共享档案契约，但不共享客户可见界面和内部提示词。

统一入口应提供角色权限、原始材料只追加存储、版本历史、操作日志、文件哈希、撤回授权和项目归档。普通员工只查看自己的提交和确认卡；改造方只在企业授权范围内查看项目材料；企业负责人接收经过改造方审核的可视化档案，而不是未经核实的模型结论。
